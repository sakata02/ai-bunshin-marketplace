# 1日スプリント：プランニング（9:00）

> 部下の呼び出しは `subagent_type: ai-bunshin:<名前>`。資料は `buka-a`（作成）→ `buka-b`（検証）、開発は `dev-a`（部下C・実装）→ `dev-b`（部下D・検証）、分析は `analyst`（部下F）→ `buka-b`、研修は `trainer`（部下G）→ `buka-b`、デザインが入るタスク（`design: true`）は作る人の前に `design`（部下E）。本人設定の `team.off` の部下は使わない。モデルと考える深さは指揮官ルールの表に従い、Opus に上げるときは理由を do_log に「Opus に上げた理由：…」と1行書く。**誰を呼ぶかはタスクの `assignee`（作る人）と `reviewer`（確かめる人）に従う**（指揮官ルールの「振り分け」）。スクリプトは `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/update_dashboard.py"`。

このあと自動で `/ai-bunshin:daily-do`（実行）が続く。計画は短く・早く終える。

引数：日付（YYYY-MM-DD、省略時は今日）。
自動実行（`claude -p`）のときは本人がその場にいない。**質問せずに最後まで進める。**
Bash は `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/update_dashboard.py" …` だけを使う。tasks.json は Read と Edit で直接直す（別のスクリプトは作らない）。

## 0. 開くかどうか

1. `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/update_dashboard.py" --plan-context` を実行する（日付を指定するときは `--today YYYY-MM-DD` も付ける）
2. 1行目が `SKIP: …` なら、何もせずに終わる
3. `04_ナレッジ/判断基準.md`、改善ログの「実施中の Try」、前日の `daily/*_振り返り.md`（「明日の要件確認」を含む）を読む
4. 前日に出した要件確認のお願い（kind 確認）に、本人の返事があるかを tasks.json の note と受け入れ条件で確かめる（朝の自動計画は会話を読めないため、tasks.json に書かれたものだけが伝わる）

## 1. 今日の容量を決める

- 目安は `--plan-context` の「今日の容量の目安」（直近3営業日の完了ptの平均。3日分たまるまでは初期値 8pt）
- 前日の振り返りで決めた「ベロシティを上げる Try」があれば、それも反映する
- 容量は整数にする。目安から ±2pt までは指揮官の判断で調整してよい（理由を計画に書く）

## 2. 見積もり

**見積もる対象**（`--plan-context` の印を使う）：🆕 前回の計画以降に登録されたタスク、🔁 要再見積もり（`reestimate: true`）のタスク、ポイントがないタスク、8pt 以上のタスク。それ以外は見積もり直さない。

- **今日やる候補**（容量に入りそうな上位）だけ、2人で見積もる（プランニングポーカー。タスクの `assignee`（作る人）と `reviewer`（確かめる人））
- それ以外の対象は、指揮官が1人で手早く付ける（完了予定日を出すため。使用量を抑える）
- 見積もり直したら `reestimate` を外す
- `assignee` が `指揮官` のタスク（調べもの・分析・設計）は、指揮官と `reviewer`（buka-b／dev-b）の2人で見積もる
- 見積もる人（作る人）には、見積もりと一緒に「どう」（作業の分け方）を返させる（下の「4. 計画を書く」の指示書の「どう」）

2人で見積もるとき：
1. タスクの `assignee`（作る人）と `reviewer`（確かめる人）に **並列で・独立して** 見積もらせる。指揮官ルールの「ポイントの基準」の表と、基準のタスク（指揮官ルールの「ポイントの基準」と、本人設定の「ポイントの基準タスク」）を渡す
2. 2人の差が 2段階以上（例：2 と 5）なら、それぞれの理由を比べて指揮官が決める
3. 8pt 以上は、5pt 以下に分割して新しいタスクとして登録する（元のタスクは分割後のタスクを depends_on にするか、完了にして note に分割先を書く）
4. **作業を始めたタスクのポイントは変えない**（ベロシティの水増しを防ぐため）

## 2.5 今日のスプリントゴール（なぜ）

- 今日のスプリントゴール（なぜ今日これをやるのか）を1〜2行で決める。本人の `04_ナレッジ/プロダクトゴール.md`（無ければ雛形の既定）とのつながりを1行で書く
- 次の「3. 今日のタスクを選ぶ」は、このゴールに近づくものから選ぶ

## 3. 今日のタスクを選ぶ

- `--plan-context` の候補を優先順に見て、容量に入るまで選ぶ
- 選ばないもの：⛔ 待ち（前提の作業が終わっていない）、本人のタスク（ポイントに数えない）
- 前日の持ち越しは、優先順位を見直したうえで優先して入れる
- 容量に少し余るときは、1pt の小さなタスクで埋める。容量を超えて詰め込まない
- **実行の順番**：要件確認の返事が要るのにまだ返事がないタスクは、順番を後ろにする（先に返事の要らないものを進め、その間に返事をもらう）
- AI のタスクが容量より少ない日は、通知の3行目で「こんなことも任せられます」と候補を1つ出す（本人設定の部署・定例から）

## 3.5 振り分けの確認

- 今日のタスクごとに `type`・`assignee`・`reviewer` が入っているか確かめ、無ければ指揮官ルールの「振り分け」で決めて入れる
- 担当（assignee）ごとの量を見て、1人に偏るなら順番を入れ替える（例：開発が多い日は部下C・D、資料が多い日は部下A・B）
- 開発のタスクは `dev_scope`（設計まで／実装まで）とモードを確かめる。設計までのタスクと speckit の案件は、実装の部下（C）を動かさない
- **自動実行（`claude -p`）のときは、開発の実装のタスク（`type: 開発` かつ `dev_scope: 実装まで`）を今日の計画に入れない**（自動実行では Git・テスト・インストールが使えないため。会話の中で進める。選ばなかった理由に「会話の中で実装」と書く）
- `design: true` のタスクは、作る人の前に部下E の作業が入るので、その分の時間も見込む。自動実行では部下E はデザインの指示書（文章）まで（Claude Design は会話の中だけ）

## 3.55 今日の予定と本人の仕事

- `--plan-context` の「今日の予定」（カレンダーをつないだ人だけ）と「本人の仕事（今日やるといいもの）」を見る
- 会議が多い日（目安：会議で4時間以上）は、本人へのお願いの期日を今日にしない・今日やるといいものを2件までに絞る
- 会議の前に準備が要りそうなもの（資料・データ・確認）があれば、通知の3行目で「◯時の◯◯の前に、△△を用意しましょうか？」と提案する（勝手にタスクにはしない）
- コネクタの人で、自動実行のため予定が読めなかったときは、通知に「予定は次に話しかけたときに確認します」と書く

## 3.6 モデルと考える深さ

- 今日のタスクごとに、指揮官ルールの「モデルと考える深さ」の表で、ふだんのままか Opus に上げるかを決め、計画の表に書く（上げる理由も）
- Opus に上げるのは1日に原則3回まで。超えそうなら、優先度の低いものは明日に回す

## 4. 計画を書く

各タスクについて、指揮官ルールの指示書の形式（ゴール／作るもの／使うデータ／受け入れ条件／守ること）を作る。「守ること」には実施中の Try を入れる。

- **どう**：指示書に「どう」の欄を置く。中身はプロダクトオーナー（指揮官）が書かない。作る人（開発者）が、最初の返事（または見積もりのとき）に、作業の分け方を書いて返す
- **これ以外はやらない**：指示書の「受け入れ条件」に「これ以外はやらない（やること／やらないこと）」の欄を必ず置く。完成の定義（本人の `04_ナレッジ/完成の定義.md`。無ければ雛形の既定）を参照させる
- **設計が要るタスク**（新しい仕組み・安全・権限）：設計の受け入れ条件を先に書いてから作る。設計の時間は惜しまない。ただし、設計を別の日・別のタスクに分けるかは、計画のときにプロダクトオーナーが必要に応じて決める（分けるかどうかで自動の1日の量が変わるため）

`01_スプリント/<今のスプリント>/daily/YYYYMMDD_計画.md`：

```
# YYYY-MM-DD 1日スプリント計画

## 3行まとめ
- 今日の約束：N件・Xpt（容量 Ypt）
- 最優先：T0XX …
- 本人へ（早めに返してほしいこと）：T0XX …（なければ「なし」）

## スプリントゴール
- なぜ今日これをやるか（プロダクトゴールとのつながり：…）

## 容量
- 目安 Apt（直近3日の平均 or 初期値）→ 今日の容量 Ypt（調整の理由）

## 見積もり（あれば）
| タスク | 作る人の見積もり | 確かめる人の見積もり | 決定 | 理由 |

## 今日のタスク
| 順 | タスク | 種類 | pt | 作る人 → 確かめる人（理由） | 受け入れ条件 |

## やらないこと
- 今日の計画全体でやらないこと（タスクごとの「やらないこと」は指示書に書く）

## 指示書
### T0XX
（ゴール／作るもの／使うデータ／どう（作る人が書く）／受け入れ条件（これ以外はやらない：やること／やらないこと）／守ること）

## 選ばなかったタスクと理由
- T0XX：⛔ T002（本人）待ち など
```

## 5. tasks.json を更新する

- `daily_sprints` に今日の行を追加する：
  `{"date": "YYYY-MM-DD", "capacity": Y, "planned": ["T0XX", …], "committed": X, "carried_over": [], "blockers": {}, "status": "計画済み"}`
  - `committed` は計画したタスクのポイント合計（スクリプトが検算する）
- 選んだタスクの `status` を `ToDo` に、`pdca` を `Plan` にする
- 本人の返事で今日のタスクが進むなら、そのお願いの `note` に「今日の計画で必要」と書く

## 6. 終わり方

- 自動実行のときは、最後の出力を「3行まとめ」の3行だけにする（Mac の通知に使われる）
- 会話の中で実行したときは、3行まとめと計画のパスを伝え、📌 お願いの行を付ける
