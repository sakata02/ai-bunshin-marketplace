# 開発の進め方

> 部下の呼び出しは `subagent_type: ai-bunshin:dev-a`（部下C・実装）／`ai-bunshin:dev-b`（部下D・検証）。スクリプトは `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/update_dashboard.py"`。

## 0. 3つを決めて、回答に1行で伝える（指揮官）

先に `.claude/ai-bunshin-details/dev.md` を読む（一度読んだら、この会話では読み直さない）。

**① どの案件か**：本人設定（`設定/config.json` の `dev.projects` と CLAUDE.md の「開発の置き場所」）から、依頼に合う案件を探す。
- 登録済み → その案件を使う
- 未登録の **新しい開発** → `dev.default_mode` で作り、案件として登録する（config.json と CLAUDE.md の両方。本人に一言伝える）
- 未登録だが **既存のシステムらしい**（システム名が出た・リポジトリの話がある）→ 場所とモードを1問だけ聞いて登録する
- 本人が依頼で「Git で」「Spec Kit 用に」「このフォルダで」と言ったら、それを優先する（登録を変えてよいか一言聞く）

**② モード**（案件の `mode`）
| モード | 作業場所 | Git | 実装 |
|---|---|---|---|
| `local` | 本人のフォルダの `05_開発/<案件>/` | 裏で `git init`、区切りごとにコミット（本人は意識しない）。push なし | ここで部下C → 部下D |
| `git` | 登録したリポジトリ | ブランチを作ってコミットまで（案件に `branch` があればそのブランチを使う。無ければ `branch_prefix` 付きの `<prefix><機能名>` を新しく作る）。push・PR・本番反映は本人 | ここで部下C → 部下D |
| `speckit` | 登録したリポジトリ（`.specify/` がある） | ブランチを作ってコミットまで | **ここでは実装しない**（設計を Spec Kit の形で渡す） |

Spec Kit 向けかどうか：次のどれかなら speckit の形で出す ― 依頼に「Spec Kit 用に」「スペックキットで」がある／案件が speckit で登録されている／対象のリポジトリに `.specify/` がある。判断の理由を1行書く。リポジトリの場所が分からないときは `02_成果物/<部署>/` に Spec Kit の標準の形（spec.md・plan.md・tasks.md）で出し、置き場所の確認をお願いにする。

**③ どこまでやるか**（tasks.json の `dev_scope`）
| 依頼の言葉 | dev_scope |
|---|---|
| 「設計しといて」「どう作るか考えて」「Spec Kit 用に設計して」 | `設計まで` |
| 「作って」「実装して」「直して」「追加して」 | `実装まで`。ただし **speckit の案件は、何と言われても `設計まで` と書く**（実装は本人側の Spec Kit で行うため） |
| どちらとも取れる | **`設計まで`**（勝手に作り始めない） |

回答の例：「T0XX は『社内ポータル』（git）で、設計までにします。設計を確認してもらってから作ります」

**案件の登録の項目**（config の `dev.projects` の1件）：`name`（案件名）・`mode`（local／git／speckit）・`path`（場所）・`type`（`開発` 以外の使い方なら。例 `記事`）・`branch`（決まったブランチで作業する案件）・`branch_prefix`（新しくブランチを作る案件）・`test`（テストのコマンド）・`note`（入稿や公開の流れなど）。そのほかの項目（記事の置き場所・プレビューなど）は `note` か、その案件のリポジトリの README に従う

**自動実行（朝の計画のあとの実行）での制限**：自動実行では Git・テスト・インストールのコマンドを許していない。開発の **実装** は会話の中で進める（朝の計画には入れない）。**設計まで** のタスクは自動実行でも進めてよい（ファイルを書くだけ。speckit のブランチ作成とコミットは、次に本人と話すときに行う）

## 1. 仕様（指揮官）

- 何を・誰のために・どんな場面で使うか、何ができたら完了か（受け入れ条件。チェックできる形で 3〜7 個）
- 本人に聞かないと決められないこと（データの場所、使う人、ほかのシステムとのつながり）は、本人へのお願い（判断・提供）にする

## 2. 設計と計画（指揮官）

- 使う技術、ファイル構成、データの流れ、テストの方針
- タスクに分ける（1つ 5pt 以下。指揮官ルールの「ポイントの基準」の「開発の場合」（`.claude/ai-bunshin-details/tasks-json.md`））
- **設計の置き場所**
  - local：`05_開発/<案件>/設計/`（仕様.md・設計.md・タスク.md）
  - git：リポジトリのブランチに `docs/` など、その案件の決まりに合わせる（無ければ `docs/<機能名>/`）
  - **speckit**：書く前に、そのリポジトリの `.specify/memory/constitution.md`（原則）と `.specify/templates/`（spec・plan・tasks のひな形）を読み、**その案件の版の Spec Kit の形** で `specs/<番号>-<機能名>/` に spec.md・plan.md・tasks.md を作る。番号は既存の `specs/` の続き。ひな形と合わない点・分からない点は【推測】と書いて本人に確認する
- **画面がある開発** は、部下E（`ai-bunshin:design`）に画面の流れとデザインの指示書を作らせる（デザインシステムは本人設定から。無ければ指揮官ルールの「デザインシステム」のとおりお願いを出す）。部下C の指示書にデザインの指示書のパスを入れ、部下D は「デザインどおりか」も確かめる
- 部下D に設計を検証させる（仕様との食い違い、タスクの粒度、speckit なら constitution とひな形に合っているか）

## 3. 設計までのとき：ここで止まる

1. 設計（と部下D の検証結果）を本人に出す
2. 本人へのお願い（判断）を登録する：「設計の確認 → 実装に進めてよいか」。期日は3営業日以内。steps に設計のパスと、見てほしい点（3つまで）
3. **speckit の案件**：お願い（設定）として、本人（またはその案件の担当）がそのリポジトリで実装する手順を出す：
   - ターミナルで `cd <リポジトリ>` → `git switch <ブランチ>`（`!` は付けない。ターミナルでそのまま打つ）→ そのフォルダで `claude` を起動 → `/speckit-analyze`（あれば）→ `/speckit-implement`
   - コマンド名は、そのリポジトリの Spec Kit の版に合わせる（`.claude/` の中のコマンド名を確かめて書く）
4. タスクを完了にする（設計のタスクとして）。**実装のタスクは作らない**
5. 本人が「いいよ」「作って」と言ったら、**実装のタスクを新しく登録** して（`dev_scope: 実装まで`、`depends_on` に設計のタスク）、4 に進む

## 4. 実装（部下C）→ 検証（部下D）

部下を呼ぶ前に、先に `.claude/ai-bunshin-details/models.md` を読む（一度読んだら、この会話では読み直さない）。

1. 部下C に指示書を渡す。指示書に必ず書くこと：作業場所（絶対パス）、モードと Git のやり方（ブランチ名）、設計のパス、受け入れ条件、テストのコマンド（案件の `test`。無ければ部下C が用意する）
2. local で初めての案件なら、先に `05_開発/<案件>/` を作り、`git init` しておく（部下C に任せてもよい）
3. 部下D が検証 → 不合格なら部下C が直す → 再検証（最大3周。ただし同じ失敗が2回続いたら3周目に入らず、作り方を見直す）
4. 依存しないタスクは、部下C を並列で動かしてよい（同じファイルを触るものは並列にしない）
5. **部下C・部下D を出すとき**：目安の時間を決めて指示書の頭に書き、do_log に `- YYYY-MM-DD T0XX 開始 HH:MM／目安 N分／見る時刻 HH:MM` を書き、更新が止まったら起こしてくれる背景のタイマーを1つだけ出す。起こされたあとの様子の見方・「今どこ？」・止め方・戻し方は `/ai-bunshin:sprint` の「部下を出したら：長引いたら様子を見る」のとおり。部下C の指示書の「守ること」には「部下は部下を呼ばない」「同じ失敗が2回続いたら3周目に入らず報告する」も書く。止めたあとの「戻す」は、本人への1行のコマンドのお願いにする

### 動いている仕組みを直すとき（見張り・hooks・自動実行のスクリプト）

見張り（`ng_guard.py`）・hooks・自動実行のスクリプト（`daily_cycle.sh`・`run.sh`）は、**直したその時から効く**。書きかけの版で全部の Bash が止まったことがある（T058）。
- 作業用のコピーで作り、テストと試しが全部通ってから、**一度に置き換える**。置き換える前に `.bak` を残し、同じ場所での改名（`mv`）で一度に切り替える
- 壊れた見張りの下では、指揮官は `Read` しか使えない。**本人用の戻しのコマンド**（例：`! mv <場所>.bak <場所>`）を、置き換える前に先に用意して、部下の指示書にも書く
- 置き換えたら、指揮官が簡単なコマンド（`date`）を1回打って、止まらないことを確かめる。打つ前に「いま動いているのは、マーケットプレイスの元か、Claude Code が読み込んでいるプラグインのコピーか」を書いてから打つ（元を直しても、動いているのはコピーのことがある）
- 見張りの自己点検：本人のフォルダの中で、`ng_guard.py --explain "date"` が pass、`--explain "rm x"` が deny を返さなければ「壊れている」とみなす。起動時のまとめの先頭と、自動実行の起動前に、同じ点検が入っている

## 5. 引き渡し

| モード | 渡すもの |
|---|---|
| local | `05_開発/<案件>/使い方.md`（何ができるか、動かし方：ダブルクリックするファイルかコマンド1行、入力と出力の場所、困ったとき）。必要なら結果を Excel・Web ページにして `02_成果物/` に置く |
| git | ブランチ名、変更点の説明、テストの結果、**PR の説明文の下書き**。本人へのお願い（送付）：push と PR の作成の手順（`! git -C <リポジトリ> push -u origin <ブランチ>` など）。本人が許可している場合（本人設定の許可する例外と `ng_allow`）だけ、push まで AI が行う |

- do_log に「作ったもの・テストの結果・D検証済み（コミット）」を書き、タスクを完了にする
- 本人が使って気づいた点は、新しいタスクとして受ける
