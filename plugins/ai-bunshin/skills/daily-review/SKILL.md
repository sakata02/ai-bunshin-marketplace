# 毎日の振り返り会議（KPT → Try → 翌日検証 → ルール改善）

> 部下の呼び出しは `subagent_type: ai-bunshin:<名前>`。資料は `buka-a`（作成）→ `buka-b`（検証）、開発は `dev-a`（部下C・実装）→ `dev-b`（部下D・検証）、分析は `analyst`（部下F）→ `buka-b`、研修は `trainer`（部下G）→ `buka-b`、デザインが入るタスク（`design: true`）は作る人の前に `design`（部下E）。本人設定の `team.off` の部下は使わない。モデルと考える深さは指揮官ルールの表（`.claude/ai-bunshin-details/models.md`。Opus に上げるか迷うときに読む）に従い、Opus に上げるときは理由を do_log に「Opus に上げた理由：…」と1行書く。**誰を呼ぶかはタスクの `assignee`（作る人）と `reviewer`（確かめる人）に従う**（指揮官ルールの「振り分け」）。スクリプトは `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/update_dashboard.py"`。

引数：日付（YYYY-MM-DD、省略時は今日）。

自動実行（`claude -p`）のときは本人がその場にいない。**質問せず最後まで進め、判断が必要なことは「本人へのお願い」に登録する。**
Bash は `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/update_dashboard.py" …` だけを使う。tasks.json は Read と Edit で直接直す（別のスクリプトは作らない）。特定のタスクだけ見たいときは、tasks.json を全体で開かず `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/update_dashboard.py" --task T0XX T0YY` で出す（指定のタスクだけを JSON で出す。読むだけで何も書かない。無い ID は知らせて終了コード 1）。直すときは必要なところを Read してから Edit する。ロックの確認のときだけ `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/lock_check.py"` も使ってよい（読むだけ）。

1日スプリント（9時 計画 → すぐ実行 → 17時 振り返り）の最後の会議。**目的は、ベロシティ（1日に完了できる pt）を上げること。**

## 0. 開くかどうか

**先に、自動実行のロックを確かめる**（自動実行・会話のどちらでも。ほかの実行と重ならないための守り）：

- `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/lock_check.py"` を実行する（読むだけ）。**ロックの判断はこの1行目だけで決める**。「⏳ 自動実行中」の表示や `.lock` の中身を自分で読んで、自動実行かどうかを決めない（自動実行の中の自分自身のロックも、その表示に出る）
- 1行目が `OPEN: …`（ロックなし／古いロック／自分の実行のロック）なら、そのまま下の手順に進む
- 1行目が `SKIP: …`（ほかの実行が動いている）なら、部下は動かさず・何も書かずに終わり、本人には「◯◯の自動実行が動いているので、重ならないよう開かなかった。終わってから声をかけてほしい」と1〜2行で伝える
- 自動実行の中では、`daily_cycle.sh` が渡した環境変数 `AI_BUNSHIN_AUTO_RUN` とロックの ID が一致するので、自分のロックでは必ず `OPEN` になる。`SKIP` が出るのは、会話から開いたとき、または別の自動実行が動いているときだけ

1. `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/update_dashboard.py" --review-context`（日付指定時は `--today YYYY-MM-DD` も付ける）を実行する
2. 1行目が `SKIP: …` なら、部下は動かさずに終わる
   - `SKIP: 振り返り済み`・`SKIP: 営業日ではない`：**何も書かない**（今日の議事録はもうある、またはいらない。上書きしない）
   - `SKIP: 今日の動きなし…`：議事録の保存先にファイルが**なければ**、次の1行だけを書く。あれば何もしない
     `# YYYY-MM-DD 振り返り — 開催なし（理由）`
3. `OPEN` なら続ける
4. 先に `.claude/ai-bunshin-details/retro-try.md` と `.claude/ai-bunshin-details/daily-sprint.md` を読む（一度読んだら、この会話では読み直さない）

## 1. 材料を集める（指揮官）

- `--review-context` の出力（今日のタスクの変更、今日完了したタスク、今日更新されたファイル、実施中の Try）
- `01_スプリント/<今のスプリント>/do_log.md` の今日の記録（全体は開かない。今日の日付（YYYY-MM-DD）を含む行を `Grep -n` で探し、続きの字下げの行も読む。日付の見出しの部分があればその部分も読む。見つからないときは全体を読む（読めないままにしない））
- 今日更新された成果物（中身を読む）
- `04_ナレッジ/改善ログ.md`（実施中の Try／定着したルール／やめた Try。**振り返りでは全体を読む**。やめた Try・定着したルールと同じ Try を繰り返さないため。似た Try が過去にあるか迷うときは `04_ナレッジ/改善ログ_保管/` も `Grep` で探す）
- `00_タスク管理/data/tasks.json`（進行中・レビュー中のタスク、期日の近いお願い）
- その日の会話の記録（今日の分の do_log の「会話」の分）から、本人が手作業でやったことを拾う（業務改善の候補。AI に頼めたはずのもの）

「今日行ったタスク」の一覧を作る（変更・完了・成果物の更新があったタスク）。部下に渡す資料はこの材料からまとめる。

## 1.5 最初の議題：チームを迷わせた仮説と真因

細かい作業の直しだけで終わらせず、チームを迷わせた仮説と真因・マインドにも目を向ける。議題は次の順に進めるが、**この議題を最初に行う**（②のタスクごとの KPT は、ここへの材料として短くまとめる）。

- 今日、チームが何を前提に動いて迷ったか（仮説）、なぜそうなったか（真因）を、指揮官が材料から仮置きし、手順 3・4 の返事で確定する
- どのプロンプト・定義（rules・skills・agents）が迷わせたかを、仮説として書く。同じ種類の問題が2回続いているなら、直し方を足さずに作り方を見直す案にする
- 手順 3・4 の呼び出しで、その日に動いた作る人・確かめる人にも意見を聞く

## 2. 議題① 昨日までの Try の検証

実施中の Try がなければ飛ばす。

1. その日に動いた担当（作る人・確かめる人。デザインが入ったタスクは部下E も。同じ部下が複数動いたときも、動いた分だけ）に **並列で**、各 Try について「今日の作業で実際にやったか／やってみてどうだったか（現場の感想）」を聞く（呼んだ部下の Agent ID は、呼んだらすぐ議事録か `do_log.md` に `- YYYY-MM-DD Agent ID: <id>（T0XX・部下C）` の1行で書く。あとで探すときは、`do_log.md` を全体で開かず `Grep` で `Agent ID:` を含む行を探して、T 番号と担当で選ぶ（この実行で書いた行＝末尾のほう）。見つからなければ新しく呼ぶ）
2. 指揮官が各 Try の「確かめ方」に照らして結果を確認し、判定する
   - **定着**：確かめ方の基準を満たした → 「ルール変更の承認」候補にする（手順 6）
   - **継続**：まだはっきりしない、または今日試す機会がなかった → 中身を直してもう1日。**開始から3営業日で決着させる**
   - **中止**：効かなかった／手間に見合わない → 「やめた Try」に理由付きで移す

## 3. 議題② 今日行ったタスクの KPT（タスクごと）

今日動いた担当（作る人・確かめる人。デザインが入ったタスクは部下E も）に、**並列で・独立して**、タスクごとに Keep / Problem / Try を出させる。聞くのは動いた担当だけ（動いていない部下は動かさない＝使用量を抑える）。呼んだ部下の Agent ID は、呼んだらすぐ議事録か `do_log.md` に `Agent ID: <id>（T0XX・部下C）` の形で書く（朝の実行の ID は、別の実行なので使えない）。タスクごとの KPT は、最初の議題の材料として短くまとめる。
指示には「今日行ったタスクの一覧と材料」「出力形式」を入れる：

```
### T0XX タイトル
- Keep：
- Problem：
- Try：（具体的に。誰が・いつ・何をするか）
```

## 4. 議題③ 行っている内容の KPT

同じ担当に、**並列で・独立して**、次の観点で KPT を出させる（手順 3 と同じ呼び出しにまとめてよい）：
- 進行中・レビュー中の成果物の出来（受け入れ条件・判断基準に照らして）
- ゴールと期日に間に合うか（遅れの見込み）
- 進め方（役割分担、指示書、検証、手戻り）

## 4.5 議題④ ベロシティ（指揮官がまとめ、その日に動いた担当に原因を聞く）

`--review-context` の「今日の計画」と「ベロシティの推移」を使う。

1. **約束 vs 完了**：約束 Xpt → 計画分の完了 Ypt（達成率）、計画外の完了 Zpt。**「自動で動いた分」と「会話の中で一緒にやった分」を分けて書く**（今日の分の do_log の各タスクの「自動／会話」から数える。ものさしは自動で動いた分。スクリプトで数えるのはこれから）
2. **終わらなかったタスクの理由を分類する**（1つのタスクに1つ、いちばん大きな理由）：
   - 本人待ち／見積もりずれ（思ったより大きかった）／要件の変更／要件の取り違え（手戻り）／手戻り（検証で差し戻し）／割り込み（`added`）／使用量の上限／障害（道具・権限・情報不足）
   - 「要件の取り違え」が続く場合は、依頼したその場で要件を詰める範囲を広げる案を出す
   - **振り分けミス**（作る人・確かめる人が仕事の種類に合っていなかった）も分類に入れる
   - 本人名義の記事を扱った日は、「本人らしさ」の KPT を1つ入れる（指揮官ルールの「文章のスタイルを育てる」＝`.claude/ai-bunshin-details/writing-style.md`）
3. **推移**：3日平均が上がっているか、下がっているか。下がっていれば理由
4. **見積もりの精度**：終わったタスクのうち、見積もりより大きかった・小さかったもの（次の見積もりの基準にする）
5. その日に動いた担当には、手順 3・4 の KPT と一緒に「何がいちばん時間を食ったか」「どうすれば同じ時間でもっと終わるか」を聞く

6. **作業中のプロダクトオーナーへの確認の数と、Opus に上げた回数**を見る。多い日は、原因（プロンプト・エージェントの定義・要件定義）のどれかを会議で決める。妥当なら許容して、理由を議事録に残す。妥当でなければ、直しを Try にする
7. **使用量**：上限に当たった・本人が使えなかった、という記録があれば書く。最初の3日（計画のある日）は、議事録の ④ に「使用量の確認のお願い」を1行入れ、本人に `/usage` の % を一言もらう（返事は次の日の容量に使う）
8. **時間の上限・手数の上限で止まった自動実行**（T095・T066）：本人のフォルダの `scripts/auto/last_timeout.txt`（1行：日時・段階・分か回・種類。種類は `minutes`／`turns`で、4列目が無ければ `minutes`。無ければ無い）を `Read` で見て、今日の日付なら、議事録の ④ に「時間の上限で止まった（段階・N分）。作業中のタスクと実行中の daily_sprints が残っている」と書く（種類が `turns` なら「手数の上限で止まった（段階・N回）。…」。「N分」とは書かない）。止まったタスクの原因（見積もり・範囲・同じ失敗の繰り返し）を会議で決める。目安の時間（暫定）は、`do_log.md` の「開始 HH:MM／目安 N分」と終わった時刻を見て、ずれが大きければ Try にする

**ベロシティを水増ししない**：完了済みのポイントを変える、受け入れ条件を緩めて完了にする、小さく分けすぎて数を稼ぐ、は改善とみなさない。

tasks.json の `daily_sprints` の今日の行を更新する：
- `carried_over`：終わらなかったタスク
- `blockers`：`{"T0XX": "分類：具体的な理由"}`
- `status`：`振り返り済み`
- 持ち越すタスクは、明日の優先順位を見直す

## 5. 反論ラウンド（②③④まとめて1回）

SendMessage で、作る人の意見を確かめる人に、確かめる人の意見を作る人に渡し、同意・反対を理由付きで答えさせる（タスクごとの作る人と確かめる人の組で行う。送る先は、この会議の手順2・3で呼んだ部下の Agent ID。呼んだときに議事録か `do_log.md` に書いたものを使う）。

## 6. 結論を出す（指揮官）

1. **タスクごとの結論**：直す作業があれば tasks.json に登録する（成果物そのものはここでは直さない）
2. **明日の Try を2〜3個に絞る**：Problem のうち影響の大きいもの、特に最初の議題の真因から。**Try の出口は、プロンプト・定義（rules・skills・agents）の変更案**にする（どのファイルの何を、どう変えるか）。その場の作業の直しだけで終わらせない。各 Try に必ず付ける：
   - ID：`Y<YYYYMMDD>-<n>`（例 `Y20261029-1`）
   - 内容（誰が・何をするか）
   - **確かめ方**（明日の振り返りで○×が付けられる形。例「部下Bの指摘のうち事実誤りが0件」）
   - 確かめ方が書けない Try は採用しない
   - **良くするものの見出し**を付ける：プラグインの品質／チームの品質／人間側のやり方（指揮官ルールの「振り返りと Try」＝`.claude/ai-bunshin-details/retro-try.md`。人間側は、出口が業務改善の提案の「候補」。確かめ方は「翌日の振り返りまでに、提案の一覧の「候補」に1行足されているか（提案にするかは金曜に決める）」などで書く）
   - 実施中の Try（継続分）と合わせて、**同時に試すのは最大3個**
   - **少なくとも1つは「ベロシティを上げる Try」にする**（議題④でいちばん大きかった理由を減らすもの）。確かめ方は数値で（例「明日の完了 pt が 3日平均を上回る」「手戻りが0回」「本人待ちで止まったタスクが0件」）
   - 本人待ちを減らす Try（例：明日必要になるお願いを今日のうちに出す）は、本人の手間を増やさない形にする
3. **ルール変更の承認**（定着と判定した Try がある日だけ）
   - その日の分をまとめて、本人へのお願いを1件登録する：
     - `assignee`: 本人の名前（config の owner）、`kind: 判断`、`title: ルール変更の承認（N件）`、`due`: 翌営業日、`due_reason`: 「承認されるまで Try のまま試し続けるため、早めに定着させたい」
     - `why`: 「AI分身の動き方を変えるため、本人の承認を得てから書き込む」
     - `steps`: ① 議事録（パス）の「ルール変更の承認」を読む ② 承認する番号を伝える（例「1と3承認」「全部OK」）③ 直したい点があれば一言
     - `done_when`: 「全件に承認／却下の返事がある」、`report_back`: 「承認した番号」
   - 1日に出すのは最大3件
   - **承認されるまでルールファイルには書き込まない**（その Try は「継続」として試し続ける）
   - **各件に行き先と理由を付ける**：
     | 行き先 | 基準 |
     |---|---|
     | **本人**（本人設定＝CLAUDE.md の「育ったルール」） | 本人の部署・相手・好み・使う道具・社内の事情に依存する |
     | **共通**（プラグインの元） | 誰が使っても同じように効く、AI の進め方そのもの。人名・部署・社内事情を含まない。**かつ** 3営業日以上効果が確認でき、別の種類のタスクでも効いた |
     | 迷ったら | **本人**（あとから共通に上げられる。共通から戻すほうが影響が大きい） |
   - 本人は「1承認」「2は本人に」のように、行き先を変えて承認できる
   - **承認の対象には、エージェントのプロンプト・定義（rules・skills・agents）を含める**。書き込み先にファイル名（例 `skills/daily-plan/SKILL.md`、`agents/dev-a.md`）を明記する

改善ログ.md の更新：
- 「実施中の Try」：明日の Try（継続分を含む）に書き換える
- 「やめた Try」：中止したものを理由付きで追記する
- 「定着したルール」：承認されて書き込んだものだけ追記する

改善ログの月ごとの保管（古い記録を消さずに別の場所へ移す。毎日の読む量を減らすため）：
- **いつ**：その月の最初の振り返りで。移せなかった月（下の「移さない」の場合）は、次に移せる振り返りでまとめて移す
- **何を**：「やめた Try」と「定着したルール」のうち、日付（やめた日・承認日）が**前の月より前**のもの（例：11月なら9月以前）。**「実施中の Try」は移さない**。ほかの部分（「過去の記録」など）も移さない
- **移す前に**：会話の中で、先に `git rev-parse --show-toplevel` を実行し、出力が本人のフォルダと一致するとき（本人のフォルダ自身が Git で記録されている）は、`git add -A && git commit -m "YYYY-MM-DD 改善ログの保管の前"` を実行して、戻せるようにする（会話の中でだけ git の add・commit を使ってよい。使ってよいのは、この手順・下の「9. 終わり方」の振り返りのコミット・指揮官ルールの「控え」の区切りのコミットだけ）。一致しないとき（親のフォルダのリポジトリなど）や Git が使えないときは、Git で記録していない環境として扱う。「コミットするものが無い」という失敗は、すでに記録されているので成功として扱う（そのまま進む）。Git で記録されていないときは、`改善ログ.md` を全体のまま `04_ナレッジ/ルール履歴/YYYYMMDD_改善ログ.md` にコピーしてから移す
- **移す**：1. 移す行を、行の日付の月ごとに `04_ナレッジ/改善ログ_保管/YYYYMM.md` へ書き足す（無ければ作る。あるファイルは上書きせず、末尾に足す。**足す前に、保管のファイルに同じ ID の行がすでにあれば足さない**（途中で失敗してやり直しても二重にならない）。見出しは「定着したルール」「やめた Try」で、表の列は改善ログと同じ）→ 2. 保管のファイルに行が入ったことを読んで確かめる → 3. そのあとで `改善ログ.md` から同じ行を外す（保管に入った行だけ。順番を逆にしない）。**消さない（移すだけ）**ので、NG の「上書きでの消去」には当たらない（中身は保管のファイルと、移す前の記録に残る）
- **移さない**：自動実行（`claude -p`）のとき（Git の add・commit が許されていないため、戻せる状態をつくれない）、Git のコミットも控えのコピーもできなかったとき、保管のファイルに書けなかったとき。その日は何も移さず、議事録の「3行まとめ」の下に「改善ログの保管：次の会話の振り返りで行う（理由）」と1行書く。自動実行で移せない月の分が溜まっているとき、**金曜の振り返りで**、本人へのお願い「改善ログの保管（次の会話で「改善ログを保管して」と言う）」を出す（毎日は出さない）。会話で「改善ログを保管して」と言われたら、この「改善ログの月ごとの保管」の手順だけを行う（振り返りの会議は開かない）
- 移したら、議事録に「改善ログの保管：N件を 改善ログ_保管/YYYYMM.md へ移した」と1行書く。移すものが無い日は何も書かない

## ルール変更が承認されたとき（本人との会話の中で）

本人から「1と3承認」などと言われたら：

**書く前に1行を見せる（見せ方の型にかかわらず同じ）**
- 承認のお願い（議事録の「ルール変更の承認」）に書く1行（「追加する文」）がそのまま書いてあり、本人が「承認」「OK」などと返したときは、その返事を「はい」として数え、もう一度は聞かない。お願いに書く1行が無かった・文が変わった（直した）ときだけ、書く前にその1行を引用して本人に見せ、「この1行を書きます。よければ『はい』」と「はい」を取る
- 書く1行が、NG・「必ず確認すること」・見張り・承認制を弱める中身なら、書かずに止めて本人に知らせる（弱める中身の案は出さない）
- 「2. 行き先に書く」のあとで、見せた1行と書いた1行が同じことを確かめる：行き先のファイルを `grep -F` で探し、見せた1行がそのまま1件当たること（引用符で壊れるときは Read で見比べる）。当たらない・2件以上なら直し、本人に1行伝える。do_log に「書く1行を見せて『はい』を取った・同じことを確かめた」を1行残す

1. 書き込む前に、元のファイルを `04_ナレッジ/ルール履歴/YYYYMMDD_<ファイル名>` にコピーする
2. 行き先に書く：
   - **本人** → CLAUDE.md（本人設定）の「育ったルール」の表に追記する（日付と Try の ID を付ける）。次の起動から効く
   - **共通** → **メンテする人（`設定/config.json` の `maintainer: true`）だけ** が、プラグインの元（マーケットプレイスのフォルダ。指揮官ルール・スキル・部下のうち該当するファイル）を直し、`.claude-plugin/plugin.json` の `version` を上げ、`CHANGELOG.md` に「バージョン・日付・何を・なぜ・どの Try から」を書く。Claude Code が読み込んでいるプラグインのコピー（`${CLAUDE_PLUGIN_ROOT}`、`~/.claude/plugins/` の下）は誰の環境でも書き換えない。配る作業（push など）は本人へのお願いにする。**メンテする人でなければ書き換えない**：本人の分は CLAUDE.md の「育ったルール」に入れて先に使い、共通に入れてほしい提案の下書き（何を・なぜ・試した結果）を `02_成果物/共通/` に作って、配布元へ送るお願いにする（送るのは本人）
