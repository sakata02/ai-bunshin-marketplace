# スプリント実行（PDCA ループ）

> 部下の呼び出しは `subagent_type: ai-bunshin:<名前>`。資料は `buka-a`（作成）→ `buka-b`（検証）、開発は `dev-a`（部下C・実装）→ `dev-b`（部下D・検証）、分析は `analyst`（部下F）→ `buka-b`、研修は `trainer`（部下G）→ `buka-b`、デザインが入るタスク（`design: true`）は作る人の前に `design`（部下E）。本人設定の `team.off` の部下は使わない。モデルと考える深さは指揮官ルールの表（`.claude/ai-bunshin-details/models.md`。Opus に上げるか迷うときに読む）に従い、Opus に上げるときは理由を do_log に「Opus に上げた理由：…」と1行書く。**誰を呼ぶかはタスクの `assignee`（作る人）と `reviewer`（確かめる人）に従う**（指揮官ルールの「振り分け」）。スクリプトは `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/update_dashboard.py"`。

> 毎日の計画・実行・振り返りは 1日スプリント（`/ai-bunshin:daily-plan` → `/ai-bunshin:daily-do` → `/ai-bunshin:daily-review`、平日9時に計画→続けて実行、17時に振り返り）で回す。この手順は、本人との会話の中で依頼をその場で進めるときと、週のスプリント（S###）の区切りの Check 会議で使う。

引数：対象のタスクID（例：`T001 T002`）または依頼内容。なければ tasks.json の優先順位上位から選ぶ。特定のタスクだけ見たいときは、tasks.json を全体で開かず `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/update_dashboard.py" --task T0XX T0YY` で出す（指定のタスクだけを JSON で出す。読むだけで何も書かない。無い ID は知らせて終了コード 1）。直すときは必要なところを Read してから Edit する。

## 0. 準備

1. `04_ナレッジ/判断基準.md`、`04_ナレッジ/部署一覧.md` を読む。`04_ナレッジ/改善ログ.md` は全体を開かず、`Grep` で見出し `## 実施中の Try` を探して、その部分だけ読む（やめた Try・定着したルールは、下の Check 会議で Try を決めるときだけ読む）
2. **会話の中の依頼は、期間内の今の S### に足す（新しい S### を作らない。期間が過ぎていたら、先に 0-3 で次の S### を作ってから、そこに足す）**。足すタスクの `sprint` には今の S### の id を入れ、ゴールと完了の定義は今の `plan.md` に追記する
3. S### が1つも無いとき、または今の S### の期間（`end`）が過ぎたときは、次のスプリント番号を決めて `01_スプリント/S###_YYYYMMDD/` を作り、tasks.json の `sprints` に次の形で追加する（`status: 進行中`・`pdca: Plan`。前の進行中スプリントは `完了` にする）。会話の中の依頼は、期間内の今の S### に足す（新しい S### を作らない）。前の進行中スプリントを完了にするときは、`retro` に一言を書き、本人への報告は下の「完了報告の形式」の形にする：
   `{"id": "S###", "start": "YYYY-MM-DD", "end": "YYYY-MM-DD", "goal": "1週間のゴール", "status": "進行中", "pdca": "Plan"}`
   - **`id`・`start`・`end` は必ず入れる**（どれかが無いと、スクリプト（update_dashboard.py）が `KeyError` で止まる）。日付は `YYYY-MM-DD`（形が違うとスクリプトが止まる）。`goal` は無くても止まらないが、Excel の「スプリント履歴」に出るので必ず書く。`status`・`pdca` が無いと、「進行中」のスプリントとして見つからず、`start`〜`end` の日付で探す動きになる

## 1. Plan（指揮官が行う）

**分析とタスク出しは指揮官の仕事。** 部下に任せない。

tasks.json に登録する前に、先に `.claude/ai-bunshin-details/tasks-json.md` を読む（一度読んだら、この会話では読み直さない）。

1. 依頼を分析する：目的、読み手、使うデータ（`03_インプット/`）、論点
2. **スプリントゴール** を1文で決める
3. **完了の定義（受け入れ条件）**（本人の `04_ナレッジ/完成の定義.md` も満たす）を、チェックできる形で 3〜7 個書く
   - 良い例：「月別・部署別の集計表があり、合計が元データと一致する」「スライドは10枚以内で、1枚目に結論がある」
   - 悪い例：「分かりやすい資料」
4. タスクに分解し、種類・作る人・確かめる人（指揮官ルールの「振り分け」）、ポイント、優先順位を付けて tasks.json に登録する
5. `plan.md` に、ゴール・完了の定義・タスク一覧・部下への指示書を書く
6. 改善ログの「実施中の Try」を `plan.md` に明記し、部下への指示書の「守ること」にも入れる
7. スプリントの Check 会議では、その期間の `daily/` の振り返り議事録も材料にする

## 2. Do

部下を呼ぶ前に、先に `.claude/ai-bunshin-details/models.md` を読む（一度読んだら、この会話では読み直さない）。本人名義の文章（記事・コラムなど）のタスクを始める前には、先に `.claude/ai-bunshin-details/writing-style.md` も読む（指示書の「守ること」に該当部分を抜き出す。部下には読ませない）。

作る → 確かめる → プロダクトオーナーの受け取りの確認 → 完了の流れと、受け入れ条件に無いことの確認は、`/ai-bunshin:daily-do` の手順5〜8と「受け入れ条件に無いことに気づいたとき」の小見出しに従う。

1. 部下に指示書（指揮官ルールの形式）を渡して起動する。依存しない作業は **同じメッセージで並列に** 起動する
   - タスクの `assignee` が作る → `reviewer` が検証 → 問題があれば作った部下が直す（資料は buka-a → buka-b、開発は dev-a → dev-b。開発は `/ai-bunshin:dev`。分析・研修・デザインが入るタスクなど、ほかの組み合わせは冒頭のとおり）
   - **合格のあとに直したとき**（本人が送る・公開する・設定に使う成果物）：確かめる人の合格を通してから渡す。合格のあとに直したら、直した差分を `git diff` か前後の比べで機械的に出し、**同じ確かめる人**に見せる。do_log に「B検証済み（確かめた時点のコミットかファイル名）」「D検証済み（同）」を書く。再確認を省いてよいのは次の2つだけで、do_log に1行残す：(a) 確かめる人が出した文をそのまま入れ、新しい決定を含まないとき（「提案どおり」）(b) 移動だけで文言・数字が変わらないと機械で比べたとき（「移動だけ（比べた結果）」）。至急で先に渡すときは「未検証」と明記して、その日のうちに確かめる
2. タスクを開始・完了するたびに tasks.json の `status` / `progress` / `pdca` / `done_date` を更新する。状態の移り方は `作業中` → `レビュー`（作る人が返したら）→ `完了`（確かめる人の合格と受け取り OK のあと）。詳しくは `/ai-bunshin:daily-do` の「状態の移り方」
3. 各部下の報告（受け入れ条件の ✅/❌）を `do_log.md` に記録する。各タスクに「自動／会話」（自動実行で動いた分か、会話の中で一緒にやった分か）も書く。記録の行は `- YYYY-MM-DD …` で始める（古い記録は直さない）
4. 部下を呼んだら、すぐ `do_log.md` に `- YYYY-MM-DD Agent ID: <id>（T0XX・部下C）` の1行を書く（呼んだ部下ごとに1行。モデルの記憶に頼らない。古い記録は直さない）。同じ実行の中で追加の依頼に SendMessage を使うときは、ここを見て使う（`do_log.md` は全体を開かず、`Grep` で `Agent ID:` を含む行を探して、T 番号と担当で選ぶ（この実行で書いた行＝末尾のほう）。見つからなければ新しく呼ぶ）

### 部下を出したら：長引いたら様子を見る（T095。止まり・同じ失敗の繰り返し・終わらないことに、本人より先に気づく）

指揮官は返事を待つ間、自分からは起きない。部下を出すときに、起こしてもらう仕掛けと、見る時刻を先に決める。
1. **目安の時間を決める**（暫定。2週間、do_log の開始・終了の時刻を見て直す）：作る＝1pt 15分・2pt 25分・3pt 40分・5pt 60分、確かめる＝作るの半分、Opus に上げたものは1.5倍。指示書の頭に「目安：N分」と書く（部下にも見える）
2. **do_log に絶対時刻で書く**（S8。文脈が圧縮されても、ここから戻れる）：`- YYYY-MM-DD T0XX 開始 HH:MM／目安 N分／見る時刻 HH:MM`（Agent ID の行とは別に1行。Agent ID の書式は変えない）
3. **背景のタイマーを1つだけ出す**（部下を出した同じ応答で。会話の中だけ。自動実行ではタイマーを出さない。自動実行の時間の上限は `daily_cycle.sh` が持つ）：Bash を `run_in_background` で、作業のフォルダ（リポジトリと scratchpad）の更新が15分止まったら終わる until ループにする。前景の sleep は使わない。Monitor は30分までなので使わない。部下ごとにタイマーは出さない
   - 例：`sleep 900; until [ -z "$(find <作業のフォルダ> <scratchpad> -type f -mmin -15 2>/dev/null | head -1)" ]; do sleep 60; done`（15分は目安に合わせて変えてよい。Windows は `sleep` の代わりに `python -c "import time; time.sleep(N)"`）
   - 部下がみな返ったら、そのタイマーを TaskStop で止める。先に返っていて起こされたときは、「もう終わっている」と確かめて何もしない
4. **起こされたら、次の3つを見る**：①git の状態（新しいコミット・未コミットの変更）②作業のフォルダの更新時刻 ③`00_タスク管理/data/ng_log.jsonl` の最後の行（`Read` で末尾を見る）
   - 進みがあれば：本人に1行で伝え、もう一度タイマーを出す
   - 進みが無ければ：部下に SendMessage で「今どこ？止まってない？（1〜2行で）」と聞く（S1）。猶予は目安の1/4（最短5分）。部下は節目で指揮官に1行の進みを送ってよい（補助）
5. **止める**：聞いたあと猶予を過ぎても進みが無い／同じ失敗を2回報告した（S2）のどちらかで、部下を TaskStop で止め、範囲を切り直す。止めたこと・切り直した範囲を本人に伝え、do_log に書く。**同じ失敗が2回続いたら、3周目に入らない**（「最大3周」より先にこちらを当てる）
6. **止めたあとの「戻す」は本人のお願い**：git の状態を見て、残す・戻すを決める。戻すときは、本人に1行のコマンドで頼む（AI の `git restore` などは見張りが止める）
7. **使用量の上限で止まったとき**（S5）：上限が戻ったら、同じ部下に SendMessage で続きを送る（新しい部下を立てない）。戻る時刻が分かるときだけ本人に伝える
8. **見張りが壊れて全員が止まったとき**（S3。ng_log に「見張りの入力を読めませんでした」が続く、または簡単なコマンドも止まる）：指揮官は `Read` しか使えない。部下も同じ壊れた見張りの下にいて戻せないので、最初から本人に1行のコマンド（`! …`）を頼む（戻しのコマンドは直す前に用意しておく）
9. **部下は部下を呼ばない**（S7）。指示書の「守ること」に書く。差し戻しの往復の上限は、**1タスクで部下を呼ぶのは、その日の合計8回まで**（S10。T066。`/ai-bunshin:daily-do` の「部下を出すとき」と同じ決まり）。数える：作る・確かめる・デザインの呼び出しと、SendMessage での続き。数えない：Check 会議、「今どこ？」の確認。その日だけ数え（持ち越したタスクは翌朝0から）、do_log の開始の行（デザインと続きも開始の行を書く）で数える。「最大3周」「同じ失敗が2回続いたら3周目に入らない」は残し、どれかに先に届いたら止める（ただし1日8回の上限だけは、自動実行では止め、会話の中では止めずに指揮官が内容を見て続けるかを決めて本人に1行伝える。上限は天井で、確かめの回数の目標ではない）
10. **本人が「様子は？」と聞いたとき**：推測で答えず、4の3つを見て答える

## 3. Check（3者レビュー会議：議題を2つに分ける）

**Check 会議は、3pt 以上のタスクを含むときか、本人が頼んだときだけ開く**（プロダクトオーナーの判断：1pt の作業に会議が走るムダを減らし、自動の量を上げるため）。開かないとき（どのタスクも 3pt 未満）は、Check と Act を飛ばして、ループ判定へ進む。「3pt 以上のタスクを含む」は、今回の作業で動かしたタスク（週の区切りの会議のときは、その S### で動かしたタスク）の中に 3pt 以上のものがあるとき（1pt を3つ、のような合算では開かない）。開かない分の改善は、夕方の振り返り（`/ai-bunshin:daily-review`）のタスクごとの KPT で拾う。

tasks.json のスプリントの `pdca` を `Check` にする。

### 議題① 進め方の改善

1. このスプリントで動いた担当（作る人と確かめる人。デザインが入ったタスクは部下E も。同じ部下が複数動いたときも、動いた分だけ）に、それぞれ **独立して** KPT（Keep / Problem / Try）を出させる（並列で依頼。Do で呼んだ部下を使い直すときは、`do_log.md` の Agent ID に **SendMessage で KPT を聞く**。新しく呼ぶときは、呼んだら、すぐ議事録（`check.md`）か `do_log.md` に `- YYYY-MM-DD Agent ID: <id>（T0XX・部下C）` の1行を書く（モデルの記憶に頼らない））
   - 観点：段取り、役割分担、指示書の分かりやすさ、手戻りの原因、時間がかかった工程、見積もり（ポイント）の精度
2. **反論ラウンド**：SendMessage（送る先は、この会議の手順1で呼んだ部下の Agent ID。そのとき議事録か `do_log.md` に書いたもの）で、作る人の意見を確かめる人に、確かめる人の意見を作る人に渡し、同意・反対を理由つきで答えさせる（1回。タスクごとの作る人と確かめる人の組で行う）
3. 指揮官が、判断基準と過去の改善ログに照らして **採用する Try** を決める（**ここだけ `04_ナレッジ/改善ログ.md` を全体で読む**。やめた Try・定着したルールと同じ Try を繰り返さないため。似た Try が過去にあるか迷うときは `04_ナレッジ/改善ログ_保管/` も `Grep` で探す）。**Try の出口は、プロンプト・定義（rules・skills・agents）の変更案**にする（その場の作業の直しだけで終わらせない）。**Try の決まりは `/ai-bunshin:daily-review` の「6. 結論を出す」の2と同じ**：ID（`Y<YYYYMMDD>-<n>`）・良くするもの（プラグイン／チーム／人間側）・確かめ方（明日の振り返りで○×が付けられる形。書けない Try は採用しない）を付け、実施中の Try（継続分）と合わせて **同時に試すのは最大3個**。数え方は `/ai-bunshin:daily-review` の「6. 結論を出す」と同じ：効いたと判定して承認待ちの Try は枠に数えない（承認まで試すのは続ける）。試す機会が無いまま「継続」にするのは1回まで。2回目も機会が無ければやめて、改善ログの「やめた Try」に理由を書き、次の振り返りで Try を決めるときの候補に戻す（その日の振り返りに1行残す）

### 議題② いま行っているものについて

1. 作る人と確かめる人（その日に動いた担当。デザインが入ったタスクは部下E も）に、それぞれ **独立して** 評価させる
   - 観点：受け入れ条件を満たしているか、本人の判断基準に合っているか、もっと良くできる点
2. **反論ラウンド**：議題①と同じく、互いの意見を渡して1回やりとりさせる
3. 指揮官が、**今の成果物にどう反映するか** を決める

### 議事録

`check.md` を次の形式で書く：

```
# S### Check会議
## ① 進め方の改善
### 作る人の意見（KPT）
### 確かめる人の意見（KPT）
### 議論（反論ラウンド）
### 結論（採用する Try：プロンプト・定義の変更案）
## ② いま行っているものについて
### 作る人の意見
### 確かめる人の意見
### 議論（反論ラウンド）
### 結論（成果物への反映内容）
## 完了の定義の判定
- ✅ / ❌ 各条件
```

## 4. Act

tasks.json のスプリントの `pdca` を `Act` にする。

1. **議題②の結論** → 今の成果物に反映する（作業は、その成果物を作った部下に指示書を出す）
2. **議題①の結論** → `04_ナレッジ/改善ログ.md` に追記する（ID・確かめ方付き。次のスプリントから適用する）
3. 判断基準に追記すべきことがあれば `判断基準.md` に追記する
4. 作業が詰まっていると分かった場合は、先に `.claude/ai-bunshin-details/team-growth.md` を読む。部下の追加（例：調査専任。研修専任は部下G がいる）または今いる部下へのまとめ直しを、指揮官ルールの「部下を増やすときのルール」（3つの条件・上限と今の人数・本人の承認）に従って本人に提案する
5. `act.md` に、実施した内容を書く

## 本人への指示（全フェーズ共通）

Plan〜Act のどこかで、本人にしかできない作業（判断・申請・送付・確認・情報提供）が出てきたら、指揮官ルールの「本人へのお願い」に従って担当が本人（config の owner）のタスクとして登録する。その作業を待つ間は、待たなくてよい作業を先に進める。

## 5. ループ判定

- **会話の中の依頼（「0. 準備」の2で今の S### に足した作業）で、足した分の完了の定義をすべて満たした** → 足したタスクを `完了` にして（`done_date`）本人に報告する。**S### 自体は完了にしない**。S### を `完了` にするのは、`end` が過ぎて次の S### を作るとき（「0. 準備」の3）だけ。そのとき `retro` に一言を書く
- **上の場合以外で、完了の定義をすべて満たした** → タスクを `完了` にして本人に報告する。S### 全体のゴールを達成しても、ここでは S### を完了にしない。S### を `完了` にして `retro` に一言を書くのは、0-3 で次の S### を作るときだけ
- **満たしていない** → Plan に戻り、未達の条件に絞って次の周回を回す（`plan.md` に「周回2」と追記）
