# スプリント実行（PDCA ループ）

> 部下の呼び出しは `subagent_type: ai-bunshin:<名前>`。資料は `buka-a`（作成）→ `buka-b`（検証）、開発は `dev-a`（部下C・実装）→ `dev-b`（部下D・検証）、分析は `analyst`（部下F）→ `buka-b`、研修は `trainer`（部下G）→ `buka-b`、デザインが入るタスク（`design: true`）は作る人の前に `design`（部下E）。本人設定の `team.off` の部下は使わない。モデルと考える深さは指揮官ルールの表に従い、Opus に上げるときは理由を do_log に「Opus に上げた理由：…」と1行書く。**誰を呼ぶかはタスクの `assignee`（作る人）と `reviewer`（確かめる人）に従う**（指揮官ルールの「振り分け」）。スクリプトは `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/update_dashboard.py"`。

> 毎日の計画・実行・振り返りは 1日スプリント（`/ai-bunshin:daily-plan` → `/ai-bunshin:daily-do` → `/ai-bunshin:daily-review`、平日9時に計画→続けて実行、17時に振り返り）で回す。この手順は、本人との会話の中で依頼をその場で進めるときと、週のスプリント（S###）の区切りの Check 会議で使う。

引数：対象のタスクID（例：`T001 T002`）または依頼内容。なければ tasks.json の優先順位上位から選ぶ。

## 0. 準備

1. `04_ナレッジ/判断基準.md`、`04_ナレッジ/改善ログ.md`（特に直近の Try）、`04_ナレッジ/部署一覧.md` を読む
2. 次のスプリント番号を決め、`01_スプリント/S###_YYYYMMDD/` を作る
3. tasks.json の `sprints` に追加する（`status: "進行中"`, `pdca: "Plan"`）。前の進行中スプリントは `完了` にする

## 1. Plan（指揮官が行う）

**分析とタスク出しは指揮官の仕事。** 部下に任せない。

1. 依頼を分析する：目的、読み手、使うデータ（`03_インプット/`）、論点
2. **スプリントゴール** を1文で決める
3. **完了の定義（受け入れ条件）** を、チェックできる形で 3〜7 個書く
   - 良い例：「月別・部署別の集計表があり、合計が元データと一致する」「スライドは10枚以内で、1枚目に結論がある」
   - 悪い例：「分かりやすい資料」
4. タスクに分解し、種類・作る人・確かめる人（指揮官ルールの「振り分け」）、ポイント、優先順位を付けて tasks.json に登録する
5. `plan.md` に、ゴール・完了の定義・タスク一覧・部下への指示書を書く
6. 改善ログの「実施中の Try」を `plan.md` に明記し、部下への指示書の「守ること」にも入れる
7. スプリントの Check 会議では、その期間の `daily/` の振り返り議事録も材料にする

## 2. Do

1. 部下に指示書（指揮官ルールの形式）を渡して起動する。依存しない作業は **同じメッセージで並列に** 起動する
   - タスクの `assignee` が作る → `reviewer` が検証 → 問題があれば作った部下が直す（資料は buka-a → buka-b、開発は dev-a → dev-b。開発は `/ai-bunshin:dev`）
2. タスクを開始・完了するたびに tasks.json の `status` / `progress` / `pdca` / `done_date` を更新する
3. 各部下の報告（受け入れ条件の ✅/❌）を `do_log.md` に記録する
4. 部下の Agent ID を控えておく（Check会議で SendMessage を使うため）

## 3. Check（3者レビュー会議：議題を2つに分ける）

tasks.json のスプリントの `pdca` を `Check` にする。

### 議題① 進め方の改善

1. このスプリントで動いた作る人と確かめる人（資料なら buka-a・buka-b、開発があれば dev-a・dev-b も）に、それぞれ **独立して** KPT（Keep / Problem / Try）を出させる（並列で依頼）
   - 観点：段取り、役割分担、指示書の分かりやすさ、手戻りの原因、時間がかかった工程、見積もり（ポイント）の精度
2. **反論ラウンド**：SendMessage で、Aの意見をBに、Bの意見をAに渡し、同意・反対を理由つきで答えさせる（1回）
3. 指揮官が、判断基準と過去の改善ログに照らして **採用する Try** を決める

### 議題② いま行っているものについて

1. 作り手と検証者（資料は buka-a・buka-b、開発は dev-a・dev-b）に、それぞれ **独立して** 評価させる
   - 観点：受け入れ条件を満たしているか、本人の判断基準に合っているか、もっと良くできる点
2. **反論ラウンド**：議題①と同じく、互いの意見を渡して1回やりとりさせる
3. 指揮官が、**今の成果物にどう反映するか** を決める

### 議事録

`check.md` を次の形式で書く：

```
# S### Check会議
## ① 進め方の改善
### 部下Aの意見（KPT）
### 部下Bの意見（KPT）
### 議論（反論ラウンド）
### 結論（採用する Try）
## ② いま行っているものについて
### 部下Aの意見
### 部下Bの意見
### 議論（反論ラウンド）
### 結論（成果物への反映内容）
## 完了の定義の判定
- ✅ / ❌ 各条件
```

## 4. Act

tasks.json のスプリントの `pdca` を `Act` にする。

1. **議題②の結論** → 今の成果物に反映する（作業は、その成果物を作った部下に指示書を出す）
2. **議題①の結論** → `04_ナレッジ/改善ログ.md` に追記する（次のスプリントから適用する）
3. 判断基準に追記すべきことがあれば `判断基準.md` に追記する
4. 作業が詰まっていると分かった場合は、3人目の部下（調査専任・研修専任など）の追加を本人に提案する
5. `act.md` に、実施した内容を書く

## 本人への指示（全フェーズ共通）

Plan〜Act のどこかで、本人にしかできない作業（判断・申請・送付・確認・情報提供）が出てきたら、指揮官ルールの「本人へのお願い」に従って担当が本人（config の owner）のタスクとして登録する。その作業を待つ間は、待たなくてよい作業を先に進める。

## 5. ループ判定

- **完了の定義をすべて満たした** → スプリント完了。tasks.json のスプリントを `status: "完了"`、`retro` に一言を書く。本人に完了報告する
- **満たしていない** → Plan に戻り、未達の条件に絞って次の周回を回す（`plan.md` に「周回2」と追記）
- **3周しても満たせない／本人の判断が必要** → 止めて本人に状況と選択肢を報告する

## 完了報告の形式

```
✅ S###「ゴール」完了
- 成果物：02_成果物/…（パス）
- 完了の定義：すべて達成（周回 N 回）
- 今回の改善（次回から適用）：…
- 本人に判断してほしい点：…（なければ「なし」）

📌 <呼び方>へのお願い（新規 N件）
- T0XX [種類] 内容（詳細は 00_タスク管理/<呼び方>へのお願い.md）
```
