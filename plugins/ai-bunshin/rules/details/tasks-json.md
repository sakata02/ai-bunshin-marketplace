## tasks.json のルール

- ID は `T` + 3桁連番。既存の最大番号 +1
- `status`：`Backlog` / `ToDo` / `作業中` / `レビュー` / `完了`（完了にするときは `done_date` を入れる）
- `priority`：1 が最優先。新規追加や順位変更のときは全タスクの番号を振り直し、重複させない
- `points`：時間ではなく **基準のタスクとの比較** で決める（下の「ポイントの基準」）。本人のタスクにはポイントを付けても数えない
- `daily_sprints`：1日スプリントの記録（`date` / `capacity` / `planned` / `committed` / `added`（割り込み）/ `pulled`（早く終わって追加で取った分）/ `carried_over` / `blockers` / `status`）。`committed` は計画時のポイント合計で、スクリプトが検算する。完了 pt とベロシティはスクリプトが tasks から計算する
- `sprints`：週のスプリントの記録（`id` / `start` / `end` / `goal` / `status` / `pdca` / `retro`）。**`id`・`start`・`end` は必須**（無いとスクリプトが止まる）。日付は `YYYY-MM-DD`（形が違うとスクリプトが止まる）。タスクの `sprint` には今の S### の id を入れる。会話の中の依頼は期間内の今の S### に足す（足し方は `/ai-bunshin:sprint` の「0. 準備」）
- `due`：AI の作業には、本人が指定した納期だけを入れる。指定がなければ `null`（完了予定日はスクリプトが自動計算する）。**本人へのお願いには、AI が決めた期日を必ず入れる**
- `depends_on`：前提タスクのIDのリスト（例：`["T002"]`）。完了予定日の計算で、前提タスクの完了後から数える
- `type`：`資料` / `調査・分析・設計` / `開発` / `本人`（「振り分け」の表）
- `assignee`：本人の名前（config の `owner`）/ `指揮官` / `buka-a` / `buka-b` / `dev-a` / `dev-b` / `design`（本人のときは「本人へのお願い」の項目も付ける）
- `reviewer`：確かめる人（`buka-b` / `dev-b`。本人のタスクには付けない）
- `design`：部下E のデザインが入るなら `true`（「振り分け」のデザインの判断）
- 開発のタスクは `dev_project`（案件名）と `dev_scope`（`設計まで` / `実装まで`）も付ける
- `department`：本人設定の「担当部署」のどれか、または `共通`
- `category`：任意。案件の名前。同じ案件は同じ名前にそろえる（登録のときは今あるカテゴリから選ぶ）。無い・空なら「未分類」として出る。名前の一覧は持たない（人ごとに違うため）
- 更新後に hook が返すタスク状況（完了予定日など）を確認し、本人への回答に使う

### ポイントの基準

| pt | 目安 | 例 |
|---|---|---|
| 1 | 文章の手直し、短い回答、tasks.json の整理 | チャットの文面を整える |
| 2 | 調査メモ1本（検証なし） | 制度・サービスの調査をまとめる |
| 3 | 調査＋設計案＋部下Bの検証1回 | 問い合わせに対する方式の設計案 |
| 5 | 複数の成果物、Excel／PowerPoint の作成、仕組みの改修 | — |
| 8 | 大きすぎる → プランニングで 5pt 以下に分割する | — |

**開発の場合**：1＝既存スクリプトの小さな修正／2＝100行程度の単機能スクリプト＋テスト／3＝画面1つの小さなツール／5＝Web アプリの1機能（複数ファイル）／8＝分割する

- 本人のフォルダで実際に終わったタスクが増えたら、本人設定の「ポイントの基準タスク」に例を足す（そちらを優先して比べる）
- **作業を始めたタスクのポイントは変えない**（ベロシティの水増しを防ぐ）。ずれは振り返りで「見積もりずれ」として記録する
